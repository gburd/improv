Mission

Build a cross‑platform, standalone multidimensional spreadsheet—inspired by Lotus Improv and Quantrix—implemented in Rust, using differential dataflow for incremental recalculation, with a native desktop GUI for Linux, macOS, and Windows.

The core promise:

Separate structure, logic, and data

Named, multidimensional models instead of cell coordinates

Instant, incremental “what‑if” modeling on large datasets

A durable, scriptable, auditable modeling environment

High‑level goals
Modeling first, grid second: Users think in categories, items, and measures, not rows/columns.

Always‑incremental recalculation: All derived values flow from a differential dataflow graph.

Robustness over ad‑hoc hacks: Strong typing, explicit dependencies, and clear error surfaces.

Cross‑platform desktop UX: A polished, keyboard‑centric GUI that feels at home on each OS.

Extensibility: Plugins for import/export, custom functions, and automation.

Core concepts
Categories, items, and dimensions
Category: A dimension of the model (e.g., Time, Product, Region, Scenario).

Item: A member of a category (e.g., 2025, Widget A, North America, Base Case).

Measure: A named variable defined over one or more categories (e.g., Revenue[Time, Product]).

The model is a multidimensional cube:

Each measure is a tensor indexed by a subset of categories.

Views are projections and pivots of this cube, not separate sheets.

Separation of data, formulas, and views
Data layer: Raw inputs (editable cells) keyed by (measure, coordinates).

Logic layer: Formulas defined over names and categories, not cell addresses.

View layer: Layouts (grids, charts, pivot views) that bind to measures and categories.

No formula is stored “in a cell”; cells are rendered consequences of the model.

Functional requirements
Modeling and formulas
Named formulas: Revenue = Price * Quantity instead of C5 = A5 * B5.

Dimension‑aware formulas: Automatic broadcasting over categories:

Revenue[Time, Product] = Price[Product] * Quantity[Time, Product]

Scoping and reuse:

Local vs global measures

Parameterized submodels (e.g., reusable “loan” or “depreciation” modules)

Type system:

Basic types: number, boolean, text, date/time, enum

Optional units/annotations (future extension)

Error handling:

Distinguish structural errors (dimension mismatch) from runtime errors (division by zero).

Propagate errors with context and source formula.

How is the improv model or more generally the idea of a spreadsheet similar or dissimilar to a relational database?
The Improv model and the relational database model look similar on the surface—both deal with structured data, dimensions, relationships, and queries—but they differ in deep architectural assumptions, semantics, and user interaction models. Below is a comprehensive, systems‑level comparison tailored to your background in CPU architecture, concurrency models, and database internals.

🧩 Core takeaway
A spreadsheet (especially Improv/Quantrix) is a live, reactive, multidimensional functional program over labeled data.
A relational database is a set‑oriented, declarative, persistent algebraic system over relations.

They overlap in data modeling, but diverge in semantics, mutability, dependency tracking, and execution models.

🧱 Structural comparison
1. Data model
Relational DB:

Data lives in relations (tables).

Each relation is a set of tuples with a fixed schema.

Normalization, keys, constraints, and algebraic operations define structure.

Improv‑style spreadsheet:

Data lives in multidimensional cubes.

Dimensions are categories (Time, Product, Region).

Measures are functions over those categories.

Structure is semantic, not positional.

Similarity: Both define structured data with named attributes.
Difference: Improv uses tensor semantics; relational uses set semantics.

🔄 Dependency & computation model
2. Execution semantics
Relational DB:

Queries are declarative; the engine chooses the plan.

No inherent notion of “reactivity.”

Updates are discrete transactions.

Spreadsheet (Improv):

Formulas define a dependency graph.

Recalculation is reactive and incremental.

The entire model is a live functional program.

This is why differential dataflow maps so naturally onto Improv semantics: the spreadsheet is essentially a continuously maintained materialized view graph.

🧮 Formula vs Query semantics
3. Language model
Relational DB:

SQL is set‑oriented, declarative, and non‑procedural.

Queries operate over relations, not individual cells.

Improv spreadsheet:

Formulas are functional expressions over named measures.

They implicitly broadcast over dimensions.

Aggregations are dimension‑aware (SUM OVER Time, etc.).

Key difference:  
Spreadsheets have implicit iteration over dimensions; SQL requires explicit grouping/joining.

🔐 Mutability & persistence
4. State model
Relational DB:

Persistent, durable, transactional.

ACID guarantees.

Data is the primary artifact.

Spreadsheet:

In‑memory, ephemeral (though saved).

No ACID semantics.

The model (formulas + structure) is the primary artifact; data is secondary.

This is why spreadsheets are dangerous for enterprise data integrity but powerful for modeling.

🧭 Schema evolution
5. Schema flexibility
Relational DB:

Schema changes are explicit, often expensive.

Strong typing and constraints.

Improv spreadsheet:

Adding a category or measure is trivial.

Dimensions can be added without rewriting formulas.

Measures auto‑broadcast over new dimensions.

This is closer to Datomic’s attribute‑centric model than to traditional relational schemas.

📊 Multidimensionality
6. Native dimensionality
Relational DB:

No native multidimensional model.

OLAP cubes are external systems layered on top.

Improv spreadsheet:

Multidimensionality is first‑class.

Pivoting is a view transformation, not a query.

This is why Improv feels like “OLAP for humans.”

🔗 Relationships
7. Referential structure
Relational DB:

Relationships are explicit (foreign keys).

Joins are explicit.

Improv spreadsheet:

Relationships are implicit through shared dimensions.

“Joins” happen automatically when measures share categories.

This is closer to relational algebra with automatic natural joins.

🧠 Semantics of missing data
8. Nulls vs non‑existent coordinates
Relational DB:

NULL is a value with special semantics.

Missing rows are distinct from NULL values.

Improv spreadsheet:

A coordinate may simply not exist.

Measures may be sparse by default.

Missing coordinates behave like missing tensor entries.

This aligns more with sparse array semantics than relational null semantics.

🧪 Scenario modeling
9. What‑if analysis
Relational DB:

Requires separate tables, temp schemas, or CTEs.

No built‑in speculative branching.

Improv spreadsheet:

Scenarios are dimensions or layers.

Branching is trivial.

Differential dataflow makes speculative deltas cheap.

This is why Improv is beloved by financial modelers.

🧰 Summary table

Data model	Relations	Multidimensional cubes
Language	SQL	Functional formulas

Mutability	Transactional	Immediate, in‑memory
Schema	Rigid	Fluid, dimension‑centric

Scenarios	Manual	First‑class
Computation	Query‑driven	Incremental, live

Map Improv semantics to differential dataflow
You’re basically asking: if Improv is a live multidimensional functional program, how do we compile that into a differential dataflow graph? Let’s wire the semantics together.

1. Core correspondence
Improv concepts → differential dataflow concepts:

Measure → Collection of (Coordinate, Value)

Coordinate (categories → items) → Key in the collection

Formula → Operator pipeline over collections

Scenario / what‑if → Additional deltas / alternative input collections

Recalculation → Propagation of deltas through the dataflow graph

So your Rust engine is essentially a materialized view system where each measure is a view, and differential dataflow maintains them incrementally.

2. Representing measures as collections
From the Rust structures we sketched:

Key:

CellKey
=
(
MeasureId
,
Coordinate
)
In differential dataflow:

rust
// For a single measure:
type Key = Coordinate;
type Val = Value;

// Collection of all cells for that measure:
Collection<G, (Key, Val)>
For all measures together, you can either:

Keep separate collections per MeasureId, or

Use a tagged key (MeasureId, Coordinate) and filter/split as needed.

Each input measure is a base collection; each derived measure is a collection computed from others.

3. Formulas as dataflow operators
Take a simple Improv formula:

Revenue[Time, Product] = Price[Product] * Quantity[Time, Product]

Semantically:

Price is a collection keyed by Product

Quantity is keyed by (Time, Product)

Revenue is keyed by (Time, Product)

In differential dataflow:

Lift inputs into collections:

rust
let price: Collection<G, (ProductId, Value)> = ...;
let quantity: Collection<G, ((TimeId, ProductId), Value)> = ...;
Join on shared dimension (Product):

rust
let revenue = quantity
    .join(&price.map(|(p, v)| (p, v))) // join on ProductId
    .map(|((time, product), (qty, price))| {
        let val = multiply(qty, price);
        ((time, product), val)
    });
Bind back to Revenue measure:

rust
// Tag with MeasureId if you use a unified collection
let revenue_tagged = revenue.map(|(coord, val)| ((REVENUE_ID, coord), val));
The key point: dimension alignment in Improv becomes join keys and projection in differential dataflow.

4. Broadcasting and dimension semantics
Improv does a lot of implicit broadcasting:

Price[Product] is broadcast over Time when used in a Revenue[Time, Product] formula.

In differential dataflow, you make this explicit:

Broadcast = join with a collection that has fewer keys, using the shared dimensions.

Example:

Price keyed by Product

Quantity keyed by (Time, Product)

Join on Product → Price is effectively broadcast over Time.

More complex dimension operations:

SUM(Revenue OVER Time) → aggregation operator:

rust
let revenue_by_product = revenue
    .map(|((time, product), val)| (product, val))
    .aggregate(|_product, vals| sum(vals));
Improv’s OVER, BY, EXCEPT clauses map to:

Group keys (which dimensions you keep)

Aggregation operators (SUM, AVG, etc.)

Projection (dropping dimensions)

5. Dependency graph → dataflow graph
You already have:

Measure with MeasureKind::Input | Derived(Formula)

A dependency graph over MeasureId from formula references.

Compilation steps:

Topologically sort measures by dependency.

For each input measure:

Create a base collection.

For each derived measure:

Compile its Formula AST into a pipeline of:

map, join, filter, aggregate, etc.

The result is a collection for that measure.

The resulting differential dataflow graph is:

Nodes: collections for measures

Edges: operators derived from formulas

This is literally incremental view maintenance for a graph of views.

6. Edits as deltas
User edits in the spreadsheet:

Change a single input cell: (MeasureId, Coordinate) -> new Value

In differential dataflow:

Represent as a delta:

rust
// +1 multiplicity for new value, -1 for old value
input_collection.update((coord, new_val), +1);
input_collection.update((coord, old_val), -1);
Differential dataflow:

Propagates these deltas through all dependent operators.

Updates all derived measures incrementally.

This is exactly Improv’s “instant recalculation” semantics, but with formal guarantees.

7. Scenarios and speculative modeling
Improv‑style scenarios:

Add a Scenario category, or

Treat scenarios as layers of deltas.

In differential dataflow:

Option 1: Scenario as dimension:

Extend Coordinate with ScenarioId.

All collections become scenario‑aware.

Switching scenario in the UI = filtering on ScenarioId.

Option 2: Scenario as alternative input stream:

Maintain separate input collections per scenario.

Derived collections are computed per scenario.

You can compare scenarios by joining on shared coordinates.

Differential dataflow is comfortable with both—scenarios are just additional keys or additional streams of deltas.

8. Error propagation
Improv distinguishes:

Structural errors (dimension mismatch)

Runtime errors (division by zero, missing input)

In your engine:

Structural errors are caught at compile time (formula type/dimension checking).

Runtime errors become values (Value::Error) in collections.

Differential dataflow:

Treats errors as just another value.

They propagate through operators, allowing you to:

Show error cells in views

Trace back to source measures via metadata in ValueError.

3. Dimension/type inference
Key rules:

Literal:

ValueType from literal.

Dim = empty (no categories).

Ref(MeasureId, DimensionSpec):

Look up measure:

value_type from Measure.

base Dim = Measure.categories.

Apply DimensionSpec:

by → keep only those categories.

over → aggregate over those categories (requires aggregation context).

except → drop categories.

BinaryOp:

For arithmetic:

Both operands must be Number.

Dimensions must be broadcastable:

One dim is subset of the other → broadcast smaller over larger.

Else → dimension mismatch error.

Result dim = union of operand dims.

For logical/comparison:

Similar, but ValueType changes.

Call(FuncId, args):

Look up function signature:

Expected types.

Dimension behavior (e.g., SUM aggregates over specified categories).

Infer result type and dim accordingly.

This phase gives you static guarantees about dimension correctness.

We want a representation that maps cleanly to differential dataflow operators.

Each PlanNode corresponds to a collection transformation:

MapUnary/MapBinary → map operator

Join → join operator

Aggregate → aggregate/reduce operator

FuncCall → combination of maps/aggregates depending on function semantics

5. Lowering TypedExpr to PlanNode
Compiler second phase:

For each TypedExpr node:

If Literal → PlanNodeKind::Literal

If Ref → PlanNodeKind::InputMeasure(measure_id) plus dimension adjustments

If UnaryOp → MapUnary

If BinaryOp:

If dims differ:

Insert broadcast joins:

Smaller dim collection joined onto larger dim collection.

Then MapBinary.

If Call:

If aggregation function (e.g., SUM):

Build Aggregate node with appropriate group_by.

Else:

FuncCall with Map semantics.

The root TypedExpr becomes the root PlanNode for the target measure.

Example: Revenue = Price * Quantity

Price → InputMeasure(PRICE) with dim [Product]

Quantity → InputMeasure(QUANTITY) with dim [Time, Product]

Binary *:

Dims differ → broadcast Price over Time:

Join on Product.

Then MapBinary(Mul).

6. Dimension‑aware joins and aggregates
Broadcast join:

Given:

Left: dim D_left

Right: dim D_right

If D_left ⊂ D_right:

join_keys_left = D_left.categories

join_keys_right = D_left.categories

Result dim = D_right.

Aggregate:

SUM(Revenue OVER Time):

Input dim: [Time, Product]

group_by = [Product]

Result dim: [Product]

The compiler encodes these rules in PlanNodeKind::Join and PlanNodeKind::Aggregate.

7. Lowering PlanNode to differential dataflow
This is the third phase, done inside a dataflow scope:

rust
fn build_collection<G: Scope>(
    plan: &PlanNode,
    ctx: &BuildContext<G>,
) -> Collection<G, (Coordinate, Value)> {
    match &plan.kind {
        PlanNodeKind::InputMeasure(m_id) => ctx.input_collections[m_id].clone(),

        PlanNodeKind::Literal(val) => {
            // broadcast literal over target dim if needed
            broadcast_literal(ctx, &plan.ty.dim, val.clone())
        }

        PlanNodeKind::MapUnary(op, child) => {
            let c = build_collection(child, ctx);
            c.map(move |(coord, v)| (coord, apply_unary(*op, v)))
        }

        PlanNodeKind::MapBinary(op, left, right) => {
            let l = build_collection(left, ctx);
            let r = build_collection(right, ctx);
            // assume dims already aligned by previous joins
            l.join(&r).map(move |(coord, (v1, v2))| (coord, apply_binary(*op, v1, v2)))
        }

        PlanNodeKind::Join { left, right, join_keys_left, join_keys_right } => {
            // project coords to join keys, perform join, reconstruct full coord
            build_join(ctx, left, right, join_keys_left, join_keys_right, &plan.ty.dim)
        }

        PlanNodeKind::Aggregate { input, group_by, func } => {
            let c = build_collection(input, ctx);
            build_aggregate(ctx, c, group_by, *func, &plan.ty.dim)
        }

        PlanNodeKind::FuncCall { func, args } => {
            build_func_call(ctx, *func, args, &plan.ty.dim)
        }
    }
}
The compiler guarantees:

Types and dimensions are consistent.

Joins and aggregates are constructed with correct keys.

The resulting collection has keys matching the target measure’s categories.

8. Error handling
Compiler phases:

Type/dimension inference:

Emit Result<TypedExpr, CompileError>.

CompileError includes:

kind (TypeMismatch, DimensionMismatch, UnknownMeasure, UnknownFunc, etc.)

Source location (if you track it in Expr).

Plan construction:

Should be infallible if inference succeeded.

Any remaining issues (e.g., unsupported function) become compile errors.

Runtime errors (division by zero, missing input) are handled by:

Returning Value::Error from apply_unary/apply_binary/build_func_call.

Propagating through collections.

Mentat schema (steering version)
Below is a concrete Mentat schema you can use as the canonical storage model for the Improv‑style spreadsheet. It’s written in a way that agents can directly implement.

1. Entity types
We’ll model four main entity types:

Category

Item

Measure

Cell (input value)

Optionally: View (later)

2. Attribute definitions (conceptual)
Use Mentat’s :db/ident, :db/valueType, :db/cardinality, etc.

clojure
;; CATEGORY
{:db/ident       :category/id
 :db/valueType   :db.type/long
 :db/cardinality :db.cardinality/one
 :db/unique      :db.unique/identity}

{:db/ident       :category/name
 :db/valueType   :db.type/string
 :db/cardinality :db.cardinality/one}

;; ITEM
{:db/ident       :item/id
 :db/valueType   :db.type/long
 :db/cardinality :db.cardinality/one
 :db/unique      :db.unique/identity}

{:db/ident       :item/name
 :db/valueType   :db.type/string
 :db/cardinality :db.cardinality/one}

{:db/ident       :item/category
 :db/valueType   :db.type/ref
 :db/cardinality :db.cardinality/one}

;; MEASURE
{:db/ident       :measure/id
 :db/valueType   :db.type/long
 :db/cardinality :db.cardinality/one
 :db/unique      :db.unique/identity}

{:db/ident       :measure/name
 :db/valueType   :db.type/string
 :db/cardinality :db.cardinality/one}

{:db/ident       :measure/value-type
 :db/valueType   :db.type/keyword
 :db/cardinality :db.cardinality/one}
;; e.g. :value-type/number, :value-type/boolean, :value-type/text, :value-type/datetime, :value-type/enum

{:db/ident       :measure/categories
 :db/valueType   :db.type/ref
 :db/cardinality :db.cardinality/many}
;; refs to category entities

{:db/ident       :measure/kind
 :db/valueType   :db.type/keyword
 :db/cardinality :db.cardinality/one}
;; :measure-kind/input or :measure-kind/derived

{:db/ident       :measure/description
 :db/valueType   :db.type/string
 :db/cardinality :db.cardinality/one}

{:db/ident       :measure/formula
 :db/valueType   :db.type/string
 :db/cardinality :db.cardinality/one}
;; serialized formula AST (e.g. JSON or your own format)

;; CELL (input value)
{:db/ident       :cell/measure
 :db/valueType   :db.type/ref
 :db/cardinality :db.cardinality/one}

{:db/ident       :cell/coord
 :db/valueType   :db.type/string
 :db/cardinality :db.cardinality/one}
;; serialized Coordinate (e.g. JSON: { "Time": "2025", "Product": "Widget A" })

{:db/ident       :cell/value-number
 :db/valueType   :db.type/double
 :db/cardinality :db.cardinality/one}

{:db/ident       :cell/value-boolean
 :db/valueType   :db.type/boolean
 :db/cardinality :db.cardinality/one}

{:db/ident       :cell/value-text
 :db/valueType   :db.type/string
 :db/cardinality :db.cardinality/one}

{:db/ident       :cell/value-datetime
 :db/valueType   :db.type/instant
 :db/cardinality :db.cardinality/one}

{:db/ident       :cell/value-enum
 :db/valueType   :db.type/long
 :db/cardinality :db.cardinality/one}

{:db/ident       :cell/error-kind
 :db/valueType   :db.type/keyword
 :db/cardinality :db.cardinality/one}

{:db/ident       :cell/error-source-measure
 :db/valueType   :db.type/ref
 :db/cardinality :db.cardinality/one}
You can keep one value attribute per cell based on :measure/value-type, or allow multiple and enforce consistency in code.

3. Coordinate serialization
For :cell/coord, define a stable JSON format:

json
{
  "Time": "2025",
  "Product": "Widget A"
}
Agents should:

Use category names and item names in the JSON for readability.

On load, resolve names back to CategoryId and ItemId.

Alternatively, you can store:

json
{
  "category_ids": [1, 2],
  "item_ids": [10, 20]
}
…but the name‑based format is friendlier for debugging and external tooling.

4. Measure formula serialization
For :measure/formula, store a serialized AST, e.g.:

json
{
  "expr": {
    "BinaryOp": {
      "op": "Mul",
      "left": { "Ref": { "measure": "Price", "dim": { "by": ["Product"] } } },
      "right": { "Ref": { "measure": "Quantity", "dim": { "by": ["Time", "Product"] } } }
    }
  }
}
Agents can:

Use measure names in the serialized form.

Resolve to MeasureId when loading.

Concrete example model: Time × Product revenue
This is a small, fully specified example that agents can implement end‑to‑end.

1. Categories and items
Categories:

Time with items: 2025, 2026

Product with items: Widget A, Widget B

Mentat transactions (conceptual):

clojure
;; Create categories
[
 {:db/id        "time-cat"
  :category/id  1
  :category/name "Time"}

 {:db/id        "product-cat"
  :category/id  2
  :category/name "Product"}
]

;; Create items for Time
[
 {:db/id       "time-2025"
  :item/id     10
  :item/name   "2025"
  :item/category "time-cat"}

 {:db/id       "time-2026"
  :item/id     11
  :item/name   "2026"
  :item/category "time-cat"}
]

;; Create items for Product
[
 {:db/id       "product-widget-a"
  :item/id     20
  :item/name   "Widget A"
  :item/category "product-cat"}

 {:db/id       "product-widget-b"
  :item/id     21
  :item/name   "Widget B"
  :item/category "product-cat"}
]
2. Measures
We’ll define:

Price[Product] (input)

Quantity[Time, Product] (input)

Revenue[Time, Product] (derived)

RevenueByProduct[Product] (derived, aggregated over Time)

Mentat transactions:

clojure
;; Price[Product]
[
 {:db/id              "measure-price"
  :measure/id         100
  :measure/name       "Price"
  :measure/value-type :value-type/number
  :measure/categories ["product-cat"]
  :measure/kind       :measure-kind/input
  :measure/description "Unit price per product"}
]

;; Quantity[Time, Product]
[
 {:db/id              "measure-quantity"
  :measure/id         101
  :measure/name       "Quantity"
  :measure/value-type :value-type/number
  :measure/categories ["time-cat" "product-cat"]
  :measure/kind       :measure-kind/input
  :measure/description "Units sold per time and product"}
]

;; Revenue[Time, Product] = Price[Product] * Quantity[Time, Product]
[
 {:db/id              "measure-revenue"
  :measure/id         102
  :measure/name       "Revenue"
  :measure/value-type :value-type/number
  :measure/categories ["time-cat" "product-cat"]
  :measure/kind       :measure-kind/derived
  :measure/description "Revenue per time and product"
  :measure/formula    "{\"expr\":{\"BinaryOp\":{\"op\":\"Mul\",\"left\":{\"Ref\":{\"measure\":\"Price\",\"dim\":{\"by\":[\"Product\"]}}},\"right\":{\"Ref\":{\"measure\":\"Quantity\",\"dim\":{\"by\":[\"Time\",\"Product\"]}}}}}}"}
]

;; RevenueByProduct[Product] = SUM(Revenue OVER Time)
[
 {:db/id              "measure-revenue-by-product"
  :measure/id         103
  :measure/name       "RevenueByProduct"
  :measure/value-type :value-type/number
  :measure/categories ["product-cat"]
  :measure/kind       :measure-kind/derived
  :measure/description "Total revenue per product"
  :measure/formula    "{\"expr\":{\"Call\":{\"func\":\"SUM\",\"args\":[{\"Ref\":{\"measure\":\"Revenue\",\"dim\":{\"over\":[\"Time\"],\"by\":[\"Product\"]}}}]}}}"
]
Agents can choose a more compact JSON representation; the important part is the structure.
