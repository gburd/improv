# Improv v0.12.0 release qualification (J3)

The road-to-1.0 plan's J3 run on the 0.12.0 release candidate:
the [v0.10.0 benchmark](2026-10-20-v0.10.0-benchmark.md)'s cases, at its sizes,
against [0.11.0's run](2026-10-25-v0.11.0-qualification.md). Rule: within 10% of
0.11.0, or explained.

## Regressions and explanations

**Engine grid peak memory, +10–15%.** `evaluate` now runs on several timely workers
(one per 10,000 cells, up to 8 and the cores). At 1M cells with
`IMPROV_ENGINE_WORKERS=1` the same build peaks at 531 MB and evaluates in 757 ms, which
matches 0.11.0's 523 MB and 868 ms; with 8 workers it peaks at 596 MB and evaluates in
207 ms. The extra 66 MB is each worker's exchange buffers and arrangements, the price of
the 3.7× speedup. `IMPROV_ENGINE_WORKERS=1` restores the old footprint.

**PG 17's first `scale.sh` again: batches 241–1,188 ms.** Two more runs right after, same
build and the same PG 17, kept all six batches in 82–112 ms. 0.11.0's first PG 17 run
did the same (220–1,742 ms), so this is now a pattern: the first `scale.sh` on a fresh
data directory, right after the 2.5M-row load, on PG 17 only. The batches are commit →
visible, so a checkpoint or autovacuum on the new 2.5M-row table during them would look
like this; PG 18's asynchronous I/O would hide more of it. Not a correctness issue and
not new in 0.12.0; left for a profile on the next box rather than the release.

**Idle worker CPU at 1,000 models: 0.12 of a core, as in 0.11.0.** Six 10 s samples read
148, 158, 117, 121, 117 and 118 ticks (`CLK_TCK` 100); 0.11.0 with its `jit = off` fix
read 108–113 ticks once settled. The first two run higher, as 0.11.0's did (144–156) until
autovacuum analyzed the catalog. A `perf` profile puts 63% of the idle cost in the per-poll SPI
queries (index scans and a subplan over `improv.model` and `improv.binding`, about 1,000
rows each, every `poll_ms = 50`) and 4% in the worker's own sweep: it grows with the
number of models times the poll rate, and at the default `poll_ms` of 200 it is a
quarter of this. Caching the catalog between changes to it would remove most of it;
recorded for the plan, not a regression.

**Mentat 1M-row import, +6%, and the 1M-cell CLI loads, +5–8%.** The soak's two PG 18
clusters ran beside this step and not beside 0.11.0's, on the same disk; the commands'
code paths did not change in 0.12.0 (number formats add one optional attribute per
measure, two measures here). Within the 10% rule.

**`1,000 random batches` commit time.** PG 17 took 19.1 s on the first run and 9.1 s on
the two reruns: the same first-run effect as the batches above. This is the client's
commit loop, not the worker.
