# Improv engine: how fully does it use differential dataflow?

Read-only design review of `crates/engine` (tree `main` @ `19211d7`, v0.11.0 plus
three test fixes) against differential-dataflow 0.13.0 and timely 0.13.0, 2026-10-25.

## Verdict

The engine uses DD as an incremental map/join/reduce executor and gets that part
right: keys are encoded the way DD wants, each edit batch is one epoch
(`advance_to`, `flush`, step until the probe passes), single-valued plans skip the
collapse, and the two-level reduce is the standard hierarchical-key trick for
big associative groups. The engine does not use what sets DD apart from a
hand-written delta engine. Nothing is arranged once and shared: every `join` and
every `reduce` builds its own private arrangement. Results are copied out through
`inspect` into host hash maps, and the API hands back whole snapshots, so
callers re-diff what DD already gave them as deltas. Every edit moves the
frontier of every operator in one big dataflow. Everything runs on one timely
worker. The biggest measured costs come from these choices and from host-side
kernels, not from DD:
- an edit costs 52–165 ms instead of 0.03–0.16 ms when the caller still holds
  the previous snapshot of a 1M-cell measure (the GUI and the pg worker both do);
- B6's 1-of-20k-measures edit costs 31–52 ms; it can be ~0.003 ms;
- windowed reductions are O(n²) per edit: a running sum over 20k items takes
  18 s per edit;
- reduction rows are twice the size they need to be (140 vs 52 B per
  arranged row).

The host-side FIXPOINT is the right call for PageRank-like bodies, and DD
`iterate` would be slower there. B5 needs a custom total-order operator, not a
better use of `reduce`. Timely's multiple workers help batch `evaluate` (3.1× at
8 workers in a prototype) and make single edits slower; they do not address B1.

## What the code does today (questions 1–7)

**1. Arrangements: none shared.** `align_with` (`dataflow.rs:858-873`) re-keys
both sides with a `map` and calls `Collection::join`, which arranges both inputs
afresh (DD `join.rs:150-151`). Every `reduce` (`dataflow.rs:725, 740-757, 760,
769`; COALESCE `:213`; the collapse `:1288`; Recurrence `:288`) arranges its input
(DD `reduce.rs:306`) and keeps an output trace. A grep for `arrange_by_key`,
`join_core`, `reduce_core`, `import` and `TraceAgent` in `crates/` finds
nothing. So PageRank's `W` is arranged twice, keyed by `Src` both times: once as
`Out = SUM(W OVER Dst)`'s reduce input, once as `M = W / Out`'s join input. The
two cannot simply share today, because the value shapes differ. The reduce
input is an `AggRow = ((Vec<u32>, u32), Vec<CellValue>)` (`dataflow.rs:438`,
built by `agg_key` at `:717`); the join input is `(CoordKey, CellValue)`.
*Measured* (one arrangement of 1M rows at 100 rows per key, `mallinfo2`): join
form 76 B/row, `AggRow` 140 B/row, an inline `(u32, u32, CellValue)` row 52 B/row.
That accounts for the PageRank breakdown on this box (`probe pagerank`, 10k/1M,
engine heap per edge):

| Target | engine B/edge | plausible holders |
|---|---:|---|
| `Out` only | 264 | worker input map ~96 + reduce input arrangement ~140 + rest |
| `M` (needs `Out`) | 467 | + join arrangement of `W` ~76 + `M`'s snapshot ~98 |
| `PR` (all) | 611 | + host step's cells and layout (v0.11.0 at 10M: 556) |

The idiomatic DD approach is to arrange `W` by `Src` once, then call
`reduce_core` and `join_core` on that one `Arranged`. Where values must differ
per consumer, the consumer computes what it needs inside its logic instead of
in a `map` before the arrangement.

**2. Iteration: host-side, and that is right for the bodies we have.**
`solve_fixpoints` (`session.rs:516-610`) runs `Host::step` (`hosteval.rs:302`,
`fill` at `:193`) once per round. It checks `distance` (`:474`) and publishes the
result on a session (`replace`, `:454`). The fallback path runs one dataflow
epoch per round. A DD `iterate`/`Variable` scope would give incremental
re-convergence after an edit, but it only saves work where the per-iteration
state barely changes. In PageRank every rank moves every round, before and
after an edge edit. The re-solve would then touch every edge at every
iteration. The commit that introduced the host step measured the dataflow round
at 0.65–1.0 s per round at 100k edges, against the host's ~4 ms (`ac7a72e`). DD
would also hold every iteration's join output in the reduce's input
arrangement: about 13 × 1M rows ≈ 1 GB at 1M edges (*estimate*). It would also
need a global Σ|Δ| reduce fed back to stop at the tolerance, because a float
loop rarely reaches DD's exact fixed point. Warm re-solve today: 0.59 s at
10k/1M (v0.11.0), 0.62 s here (*measured*). DD `iterate` would win only for
bodies that converge exactly and locally (reachability, shortest paths, label
propagation over integers or booleans). Nobody has asked for that yet.

**3. Incremental reductions.** DD `reduce` hands the closure the key's whole
input. RANK (`statistical.rs:770`) rebuilds `Rows` for the whole group
(`agg_rows`, `dataflow.rs:510-546`: two heap allocations per row), sorts, and
emits n outputs. DD then diffs them against the n old outputs, and `settle`
(`session.rs:620`) sorts the round's deltas. *Measured* at 1M items: edit "new
max" median 1.24–1.71 s, "tail +0.5" 0.83–1.14 s. Profile: `memcmp` 12.5 %,
`per_item_ok` 6.5 %, `memmove` 6.4 %, `agg_rows` 5.6 %, `settle` 4.5 %, plus DD
merge batcher and malloc/free. A hierarchical key does well for SUM (two-level:
0.54 ms per edit at 1M here, *measured*). For RANK it does not bound the work:
items under a changed upper bucket all re-join and then consolidate to nothing.
`count`/`threshold` give per-key counts, not ranks. DD's own `count_total` and
`threshold_total` (`count.rs:47`, `threshold.rs:42`) show the pattern that fits:
an operator for **totally ordered timestamps** that keeps its own per-key state
and emits only changes. Improv's `u64` epochs are totally ordered.

**Windows are worse, and new.** `windows()` (`dataflow.rs:792-827`) builds each
row's window by scanning every row of the group (`pick`, `:812`). That is O(n²)
per group, on every edit and in `evaluate`. *Measured*:
`SUM(X OVER W[FIRST..THIS])` costs 0.92 s per edit at 5k items and 18.4 s per
edit at 20k (evaluate 17.5 s). `THIS-1..THIS` costs 166 ms per edit at 20k. The
running total is the documented example (`docs/src/formulas.md:307`).

**4. Dataflow structure and progress.** One `worker.dataflow` per engine
(`session.rs:706`). One `inspect` per measure (`:722`). One probe on a
concatenation of every output (`:748`). Each round advances **every** input
session (`run_to`, `:763-770`). So every operator's frontier moves, whether or
not data reaches it. *Measured* `probe measures`, 20k measures: fan median
134 ms, chain 120 ms, split (the edit reaches 1 measure) 31–52 ms. At 5k
measures split costs 6.9 ms; at 2 measures, 0.02 ms. Profile of split at 20k:
the reachability worklist `BinaryHeap::pop` 41 %, `propagate_pointstamps` 15 %,
`Subgraph::schedule` 5.7 %, `ChangeBatch::compact` 5 %, sorting pointstamps 5 %.
About 75 % of an edit is timely progress tracking. *Measured* prototype (plain
DD, 20k `map + inspect` measures over 100 cells), ms per round:

| Layout | fan | split (1 measure reached) |
|---|---:|---:|
| as the engine: one dataflow, inspect per measure, all inputs advance | 68.5 | 33.9 |
| one `inspect` after a tagged concat | 44.1 | 23.9 |
| one dataflow per measure, step only the edited one | — | 0.26 |
| one dataflow, a probe per input-connected group, advance only the edited group's inputs | — | **0.003** |

Epoch handling (one `u64` per batch, `advance_to` then `flush` on every session,
`while probe.less_than(&t) { worker.step() }`) is the textbook DD loop. The
cost lies in which sessions it advances.

**5. Batching, compaction, reads.** `Engine::apply` puts a whole batch in one
epoch (`session.rs:820-836`). The pg worker sends a whole poll's transactions as
one batch (`worker.rs:1521`). Good. No trace handle leaves an operator, so
compaction is the operators' own: join and reduce set logical and physical
compaction to their input frontiers (DD `join.rs:583-602`, `reduce.rs:614-619`).
*Measured*: 80,000 single-cell edits on a 1M-cell grid grew the heap by 1.8 MB.
Traces stay bounded; nothing to fix. Results are read through `inspect` into
`Arc<Mutex<Snapshot>>` (`session.rs:722-745`; `evaluate` at `dataflow.rs:1395`
takes a lock per record). Results are never read from arrangements. The
snapshot is copy-on-write (`settle`, `session.rs:636-639`): if the caller still
holds the previous `Snapshot`, a changed measure is cloned whole. The code's
own `ponytail` note says so (`session.rs:68`). *Measured* (1M-cell
`Revenue = Price * Quantity`, one-cell edits): median **52–165 ms** with the old
snapshot held, **0.03–0.16 ms** with it dropped. The GUI holds it
(`gui/src/app.rs:1441`, `self.snapshot`); its "50 ms of recalc per edit" in H3 is
this copy. The pg worker holds `l.snapshot` across `engine.apply`
(`worker.rs:1521`) and then re-diffs every changed measure in `write_changed`
(`:1530-1543`, its own `ponytail` note).

**6. Workers: all single.** Both `evaluate` and the live engine use
`execute_directly` (`dataflow.rs:1379`, `session.rs:678`). (Steering §11 says
"the engine uses timely/DD's dataflow execution, which parallelizes operators";
it does not.) *Measured* prototype (DD 0.13, broadcast join + SUM over T, 1M
cells, this box):

| workers | 1 | 2 | 4 | 8 |
|---|---:|---:|---:|---:|
| build + run | 680 ms | 382 ms | 281 ms | 222 ms |
| one edit | 0.15 ms | 0.15 ms | 0.19 ms | 1.96 ms |

Workers pay off for batch evaluation and hurt interactive edits. They do nothing
for B1, whose serial part is the background worker's main thread (decode, fold,
SPI writes, `worker.rs:746-778`). Each model's engine already runs on its own
thread; `Engine::apply` just blocks on it.

**7. Other places the code works against DD.**
- Whole snapshots out, re-diffed by callers (above). DD hands out deltas: the
  `net` vector in `settle` is exactly the round's consolidated change.
- Fat records: `AggRow` holds two `Vec`s per row (140 vs 52 B arranged); n-ary
  calls and recurrences carry `Vec<CellValue>` rows (`dataflow.rs:262-283,
  375-391`).
- Per-record `Mutex` locks in the `inspect` closures (`session.rs:730`,
  `dataflow.rs:1397`); `inspect_batch` would take one lock per batch.
- A parameter lookup is a cross product (`dataflow.rs:684`, its own note): DD's
  answer is to arrange the table by the lookup key. Not measured.
- The worker keeps its own map of every input cell to know what to retract
  (`session.rs:778, 824-831`, ~96 B/cell). DD's `arrange_from_upsert`
  (`upsert.rs:129`) does exactly this. The win is small unless a downstream
  join can reuse that arrangement, and the FIXPOINT host step reads the map.

## Ranked recommendations (biggest win first)

### 1. Return the round's delta; stop cloning and re-diffing snapshots

- **What.** Add `Engine::apply_delta(edits) -> Delta`: the consolidated `net`
  vector `settle` already builds, per measure `(key, old, new)`. Callers keep
  their own view (the GUI's grid map, the pg worker's written rows). Keep
  `apply` for compatibility. Callers that move to deltas must drop their
  `Snapshot`, or the engine must keep its state outside the shared `Arc`.
- **Files.** `session.rs` (`settle`, the reply), `gui/src/app.rs`
  (`push_engine`, the undo path), `pg_improv/src/worker.rs` (`apply`,
  `write_changed`), `tui`/`server` callers optionally.
- **Gain.** *Measured*: a 1M-cell edit goes from 52–165 ms to 0.03–0.16 ms of
  engine time. The pg worker's `write_changed` goes from O(cells of each changed
  measure) to O(delta) (*estimate*).
- **Risk.** Low. The engine already computes the delta, and snapshot equality
  tests can compare a delta replay against `apply`.
- **Size / item.** S–M. **New** (unblocks H3's "recalc per edit"; helps B1 by
  shortening applies).

### 2. Advance only the inputs an edit touches, per connected component (B6)

- **What.** At build, union-find the measure graph (inputs and derived, by
  reads) into components. Give each component its own probe over its outputs.
  In a round, advance and flush only the sessions of components the batch
  touches, and step until those probes pass `t`. An untouched session stays at
  its old time, which is safe: no operator joins across components. FIXPOINT
  sessions belong to their body's component.
- **Then, cheaper in-component.**
  - Tag every output with its measure id and `concat`, then use one
    `inspect_batch` instead of one `inspect` per measure (*measured* in the
    prototype: −36 % per round on a 20k fan).
  - Fuse map-only (`functional`, maps of one input) plans that read the same
    input into one `flat_map` emitting `(mid, key, value)`. That shrinks the fan
    and chain shapes, where all 20k measures sit in one component (*estimate*:
    134 ms → a few ms at 20k).
- **Files.** `session.rs` (`worker_loop`, `run_to`, `solve_fixpoints`'s `run`),
  `dataflow.rs` (`build_derived` returns components).
- **Gain.** *Measured* in the prototype: 33.9 ms → 0.003 ms per round for an
  edit reaching 1 of 20k measures. The engine's `split` probe is 31–52 ms now.
  B6's acceptance is < 5 ms.
- **Risk.** Medium:
  - per-input times diverge, so `inspect`'s `t > 0` seed test and the FIXPOINT
    `t` bookkeeping need care;
  - a model that is one big component gains nothing from this step (the fusion
    step is for that).
- **Size / item.** M (B6 has it as L; the per-component probe avoids separate
  dataflows). **B6.**

### 3. Make windowed reductions incremental (O(n²) today)

- **What.**
  1. Host kernel first. For decomposable functions, `windows()` uses prefix
     sums: `FIRST..THIS` is a running fold, `THIS-a..THIS+b` a sliding window,
     O(n) per group. Others use two pointers over the sorted positions instead
     of a full `pick` scan per row.
  2. Then the DD shape: block the window category as `two_level` does, so an
     edit re-reduces its block. Each item then combines its block's prefix with
     the preceding blocks' parts. DD's `algorithms::prefix_sum` exists, but it
     iterates log n rounds; the blocked form fits the existing code better.
- **Files.** `dataflow.rs:792-827`, `hosteval.rs` (`emit` calls `windows`),
  `reduce/two_level.rs`.
- **Gain.** *Measured* today: 18.4 s per edit at 20k items, 0.92 s at 5k. Step 1:
  *estimate* ~1 ms at 20k for evaluate and edits alike (the whole group still
  re-runs, but linearly). Step 2: *estimate* sub-millisecond edits at 1M items,
  like SUM.
- **Risk.** Low for step 1, because results must match the current kernel
  bit for bit. SUM and AVERAGE through `exact.rs` stay exact. MIN/MAX sliding
  windows need a monotone deque.
- **Size / item.** S (step 1), M (step 2). **New** (B5's "per-item reductions"
  in spirit).

### 4. Slim reduction rows, then share `W`'s arrangement (B8)

- **What, in order.**
  1. Change `AggRow` to inline storage: `SmallVec<[u32; 1]>` positions and
     `SmallVec<[CellValue; 1]>` values, which covers the common one-category,
     one-input reduction. In the arrangement probe this cut 140 → 52 B per row
     (*measured*, for the plain inline tuple; SmallVec headers add a little).
     Every reduction input shrinks, RANK's and the grids' included, and
     `memcmp`/malloc in the RANK profile go down.
  2. Arrange each reduced or joined measure once per key: an
     `arrange_by_key` handle cached by `(measure, key categories)`. Run the
     reduce as `reduce_core` on the join-form arrangement, computing positions
     inside the closure from the coordinate. Run the join as `join_core` on the
     same handle.
  3. B8's "host step reads M from the arrangement" stays an open question:
     reading a trace means a cursor walk each refresh. Reading the snapshot's
     `Arc` without copying into `Cells` is simpler.
- **Files.** `dataflow.rs` (`AggRow`, `agg_key`, `agg_rows`, `build_aggregate`,
  `align_with`, `build_coll`'s plumbing of a handle cache), `hosteval.rs`
  (shares `AggRow`).
- **Gain.**
  - Step 1: *estimate* −70 to −88 B per edge. PageRank at 10M drops from
    556 to ~470–490 B/edge, which may meet B8's 500 alone.
  - Step 2: *estimate* another ~76–140 B per shared row.
  - Grids: about −80 B per reduced cell (*estimate*).
- **Risk.** Low for step 1 (a type change; goldens and the host/dataflow
  bit-equality tests cover it). Medium for step 2: the reduce closure must
  reproduce the dataflow's sort order. Today `AggRow`'s `Ord` gives item order
  for free; on a shared arrangement the closure must sort by position itself.
- **Size / item.** S (1), M (2). **B8**, and helps **B5**.

### 5. An order-statistics operator for RANK, PERCENTRANK, SORTBY (B5)

- **What.** A custom operator for `TotalOrder` epochs, modeled on DD's
  `count_total`/`threshold_total`: `unary_frontier` on the keyed stream, per group a
  B-tree or Fenwick tree of `(value, item)` counts. On a retract a / insert b it
  emits rank changes only for items whose values lie between a and b, and holds
  output capabilities as `count_total` does. SORTBY uses the same structure,
  emitting the shifted slot range. Errors and non-numbers follow
  `per_item_ok`'s rules.
- **Files.** New `reduce/order.rs` (operator), `dataflow.rs` (route
  `per_item` RANK-family and SORTBY to it), and `hosteval.rs`, unchanged (the
  host step can keep the batch kernel).
- **Gain.**
  - Tail edit: *estimate* 0.8–1.1 s → ~1 ms at 1M.
  - New max: inherently O(n) output, *estimate* 1.2–1.7 s → 0.2–0.4 s, then
    bounded by `settle` and the snapshot (item 1 helps).
  - Before this, item 4's step 1 plus reusing `agg_rows` buffers: *estimate*
    20–40 % off today's RANK edits.
- **Risk.** Medium-high:
  - hand-written frontier and capability logic, which is exactly where DD
    operators go wrong;
  - needs a hegel property against `reduce::per_item` over random edit
    sequences.
- **Size / item.** L. **B5.**

### 6. Multi-worker `evaluate` for the batch paths (new)

- **What.**
  - Run `evaluate_here` on N timely workers, `Config::process(n)`, for
    `improv eval`, DuckDB `improv()` (`duckdb_model/src/lib.rs:513`) and pg
    trigger/commit mode (`pg_improv/src/trigger.rs:255`).
  - Keep the live `Engine` single-worker (edits get slower with workers,
    *measured*).
  - Required changes:
    - emit `Items`, `Literal`, `constant`, FILL grids and both-literal maps
      (`dataflow.rs:97, 173, 191, 357, 836`) on worker 0 only; today each
      worker would emit a copy;
    - feed each worker a share of the input cells;
    - spawn the worker threads ourselves with `ENGINE_STACK`: timely's
      `initialize_from` spawns threads with the default stack
      (`timely_communication initialize.rs:313`), but `Process::new_vector` and
      `Worker::new` are public;
    - plans with FIXPOINT stay single.
  - In pg, the threads must inherit the blocked signal mask, as `start_engine`
    (`worker.rs:1642`) does.
- **Gain.** *Measured* in the prototype: 3.1× at 8 workers (680 → 222 ms) on a 1M
  join + reduce. *Estimate*: about half of DuckDB's 4.5 s at 2.5M cells (B10)
  is the engine.
- **Risk.**
  - Medium: thread spawning in Postgres backends and in the DuckDB process
    (thread caps);
  - determinism holds (a key's reduce input is sorted, on one worker);
  - peak memory rises slightly from exchange buffers.
- **Size / item.** M. **New** (B10 follow-up).

### 7. B1: overlap models' engine work in the one worker (not timely workers)

- **What.** Split `Engine::apply` into `submit(edits)` and
  `try_reply()`/`reply()`. In `worker.rs`'s poll loop, map and submit every
  model's batch, then write each model's results as its reply arrives. Advance
  the slot only once every model has written. The engine threads already exist,
  so this needs no `shm_mq`/DSM.
- **Gain.** *Estimate*: a poll costs about the slowest model's engine time
  instead of the sum. Whether that meets B1's < 200 ms for a fifth model depends
  on how much of a slow apply is engine rather than SPI. Not measured; see the
  open questions.
- **Risk.** Medium. Error and rebuild paths per model, ordering within a model
  (one batch in flight per model keeps it), and Postgres errors unwinding while
  replies are outstanding.
- **Size / item.** M. **B1** (partial).

### 8. Do not upgrade DD for 1.0, but correct the pin's premise

- **Finding.** DD 0.25.1 + timely 0.31.0 build and run a reduce on rustc
  1.97.0 (`/tmp/ddrev-up`, *measured*: compile and one run only). Steering §2's
  claim that newer DD needs a newer rustc held for the 0.13.7/timely 0.19 pair.
  It does not hold for the current line.
- **Cost.** The API is new: `Collection<'scope, T, C>`, operators as inherent
  methods, no `Reduce` trait, `probe_with(&mut)`. That touches every operator
  call in `dataflow.rs` (3.8k lines) and `session.rs`, plus the four lockfiles.
- **Gain.** Unmeasured: columnar containers and a newer merge batcher could
  lower bytes per row.
- **Size / item.** L. **New**: record it in §2 and revisit after 1.0.

## Already idiomatic: keep

- The key and value encoding: `CoordKey` as `SmallVec<[(u32,u32);3]>`,
  `CellValue` as `Ord` data, `isize` diffs (`lib.rs`).
- One epoch per batch; `advance_to` + `flush` + step until one probe passes
  (`session.rs:763-770`); one probe on a concatenation (`:748`).
- `functional` skipping the collapse reduce, and `broadcast_of` building one
  join (`dataflow.rs:1234-1300, 879`). Both remove arrangements DD does not need.
- The two-level reduce (`reduce/two_level.rs`) with exact sums: the
  hierarchical-key pattern, made bit-exact. 0.54 ms per edit at 1M items here.
- `mark_sparse` choosing flat reduces for sparse groups (`dataflow.rs:1130`).
- COALESCE and PREV-with-default built from `distinct`/`threshold`/`negate`
  (`dataflow.rs:201, 341`).
- Leaving compaction to the operators: bounded over 80k edits (*measured*).
  If any trace handle is ever kept outside an operator (items 4, 5), it must
  advance `set_logical_compaction`/`set_physical_compaction` every round, or it
  will pin history.
- The host-side FIXPOINT for float bodies whose cells all move (question 2),
  with the dataflow-round fallback. Its delta step (B8 part 2: feed only moving
  cells once few move) is the right next step, and it is host-side too.
- `settle`'s per-round consolidation: needed once outputs are uncollapsed.

## Open questions

1. What fraction of a slow pg apply (B1's 1 s) is engine time vs decode, fold
   and SPI writes? That decides whether item 7 meets B1's acceptance.
2. Do real models fall into independent components (item 2)? pg models with
   many bindings probably do. One GUI model with a shared `Price` probably
   does not, which leaves the fusion half of item 2 doing the work.
3. Is item 4 step 1 alone enough for B8's 500 B/edge at 10M edges? Needs a run
   at 10M (≈16 GB, not possible on this box).
4. The parameter-lookup cross product (`dataflow.rs:684`): how large do lookup
   tables get in practice? Not measured.
5. Would DD 0.25's containers cut bytes per row enough to matter
   (recommendation 8)? Not measured.
6. Will anyone write a FIXPOINT that converges exactly and locally (graph
   reachability over booleans)? If so, routing those bodies to DD `iterate` is
   where DD's re-convergence pays; until then it is not worth building.
7. Under load, RANK's measured edit times varied 2× between runs (0.83–1.14 s
   tail). The ~5 % RANK slowdown noted in the v0.11.0 qualification is below
   this box's noise. It was not chased.
8. Stale text found on the way, no action taken:
   - `AGENT_ENGINE_STEERING.md` §11 says operators run in parallel; they do not.
   - `AGENT_OUT_OF_CORE_DESIGN.md` §3b says `CoordKey` is a `Vec`.
   - The `dataflow.rs` module header says the same.
