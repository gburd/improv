# Improv: the road to 1.0.0

Date: 2026-10-21. Baseline: `main` at c4b601b (0.10.0 released; pg_improv 0.11.0 unreleased).

This plan lists everything that has to land before Improv calls itself 1.0.0.
It comes from:

- the v0.10.0 benchmark (`2026-10-20-v0.10.0-benchmark.md`), and the fixes
  that followed it;
- the 2026-10-21 review of where Improv is not finished, does not scale, or
  is the wrong tool;
- the maintainer's additions: an operations docs set, man pages for every
  tool, a TUI/GUI review, and a web-GUI evaluation.

## How to read this plan

Each task has:

- an id;
- a one-line statement of the problem, with its evidence;
- the change;
- an **acceptance** line, which is what has to be true for the task to
  count as done.

"Benchmark" means the harnesses in `docs/reviews/bench/` and the v0.10.0 report's
probes (`crates/engine/tests/probe.rs`). A task that changes performance reports
before and after on the same harness, release build, same instance type (c7i.8xlarge
or larger, noted).

Status markers: **[open]**, **[in flight]**, **[done]** (with the commit).

**Sizing.**
- **S** is a day or less.
- **M** is a few days.
- **L** is a week or more, and needs a design note first.

- the scoped `what_if`;
- linear `add_item`;

- two-level reductions;
- fewer operators per measure;

| B1 | **Parallel apply in the logical worker.** One worker serves every model in a database on one core, so a slow model delays every other. Apply models in parallel: for example, a pool of dynamic background workers, one per busy model, under a configurable `improv.max_apply_workers`. The order within a model must stay the same, and the shared slot must still advance only after every model has applied the batch. **Acceptance:** with 4 models whose applies take 1 s each, a change to a fifth model is visible in < 200 ms; `logical.sh` and `scale.sh` pass; the shared-slot crash semantics are unchanged. **Deferred (design note, 2026-10-23).**
<br>*Design.* A model's live state (`Live`: model, fold state, and an engine running as a thread of the worker process) cannot move between processes, so each apply worker owns its models for as long as it runs: model → worker by `model_id % improv.max_apply_workers` (0 = today's serial apply). The main worker keeps the slot. Each poll it decodes once and routes as now. Each model's new transactions (raw pgoutput rows, plus the Relation messages they use) go to its worker over a `shm_mq` in one DSM segment, set up with the pool. A worker applies one model's share at a time in its own transaction: `tick` as today, recording `sync_state.confirmed_lsn` with the result writes, then replying `(model, end_lsn)` or the error. Order within a model holds: one queue per worker, and one batch per model in flight. To meet the acceptance, the main worker does not wait for slow models. It keeps polling, and moves the slot to the least end LSN that every live model has applied (a failed model is left out, as now, since it rebuilds from its tables). So the slot still moves only past what every model applied, and a crash re-reads from it; each model skips what its `confirmed_lsn` holds, unchanged. A dead worker's models are marked failed and rebuild in its replacement. A dead main worker detaches the queues, and the apply workers exit.
<br>*Why deferred.* (1) A peek returns at most `max_changes` from the slot's position. While a slow model holds the slot back, every poll re-decodes the same window, and a fast model sees nothing past it until the slow one catches up. Fixing that means advancing the slot past a slow model's backlog: a second slot, or a durable queue table. Either changes the crash semantics the task says to keep. (2) pgrx 0.17 has no `shm_mq` or DSM wrapper. The queues, worker launch and supervision, and the main worker's non-blocking reply loop are raw `pg_sys` FFI in signal- and error-sensitive code, roughly 1,000 lines plus tests, and the podman gate takes about an hour per run. (3) The smallest version, hand off each model's share and wait for all of them before advancing, is correct but fails the acceptance: a change that arrives while the slow models apply waits for the barrier (about 1 s), and its own apply runs only after that. What it does give: one poll costs the slowest model's apply rather than the sum, and a big model's rebuild (5.3 s at 2.5M rows) no longer stalls the others. If 1.0 needs only that, it is an M on top of this design.
<br>*Until then.* `capacity.md` ("The limit is the single worker") documents the serial apply. A model whose rebuilds or applies are slow can use `trigger` or `commit` mode, so it no longer delays the logical models. | L |

## 1.0.0 exit criteria

Improv is 1.0.0 when all of these hold:

1. **No open blocker:** A1 landed; every task in B–J is done or explicitly
   moved to "Not planned for 1.0" below, with a reason.
2. **Security:** C1–C3 done. The worker respects RLS and privileges, there is
   a privilege model, and the external review is closed.
3. **Operations:**
   - failover (D1), pg_upgrade (D2) and backup/restore (F5) are tested by
     scripts in CI or in J3;
   - resource limits fail safe (D7);
   - the 72-hour soak passes (J4).
4. **Documentation:**
   - F1–F7 are published; F8's tutorials run in CI;
   - every CLI tool has a man page (G2) generated from its parser (G1);
   - F10's review is done.
5. **Front ends:** H1's findings closed or deferred with reasons; H2's
   accessibility blockers fixed; I1 decided (and I2 built if the decision is
   to ship a web GUI in 1.0; it is not: see I1).
6. **Stability promise:** J1 published, and the formula language, SQL API,
   file schema, CLI and HTTP API reviewed against it.
7. **Quality gate:** the existing gate (fmt, clippy, tests, coverage ≥ 90%,
   docs, Verus, GUI golden, pg_improv on PG 15–18, DuckDB 1.5.6 + 2.0) green,
   and the scale regression gate (B11) green.
8. **Qualification:** J3 run on the release candidate, numbers in the
   release notes.

## Not planned for 1.0

Each entry below is moved here only with a reason.

- **A billion-row engine.** Out-of-core is decided in B7, but building it is
  not a 1.0 requirement. The 1.0 promise is "models whose cells fit in
  memory", with the limits stated in F2 and F4.
- **A web GUI (I2) and multi-user editing (I3).** I1 decided (c) for 1.0:
  the `/v1` HTTP API, documented, is what a web front end builds on. The
  spike (`crates/gui_web`, branch `work/web-spike`) shows the egui GUI runs
  in a browser over `improv-server`; what I2 needs first is server work (a
  GUI-shaped API, a change feed, static hosting) and an answer for screen
  readers, since egui's web runner drops AccessKit. See
  `docs/reviews/2026-10-22-web-gui.md`.
- **Replacing a graph database.** FIXPOINT covers iterative models like
  PageRank up to the tested size; F2 says where to stop.
