# Improv: the road to 1.0.0

Date: 2026-10-21. Baseline: `main` at c4b601b (0.10.0 released; pg_improv 0.11.0 unreleased).

This plan lists everything that has to land before Improv calls itself 1.0.0.
It comes from:

- the v0.10.0 benchmark (`2026-10-20-v0.10.0-benchmark.md`), and the fixes
  that followed it;
- the 2026-10-21 review of where Improv is not finished, does not scale, or
  is the wrong tool;
- the maintainer's additions: an operations docs set, man pages for every
  tool, a TUI/GUI review, and a web-GUI evaluation.

## How to read this plan

Each task has:

- an id;
- a one-line statement of the problem, with its evidence;
- the change;
- an **acceptance** line, which is what has to be true for the task to
  count as done.

"Benchmark" means the harnesses in `docs/reviews/bench/` and the v0.10.0 report's
probes (`crates/engine/tests/probe.rs`). A task that changes performance reports
before and after on the same harness, release build, same instance type (c7i.8xlarge
or larger, noted).

Status markers: **[open]**, **[in flight]**, **[done]** (with the commit).

**Sizing.**
- **S** is a day or less.
- **M** is a few days.
- **L** is a week or more, and needs a design note first.

## A. Blocker in flight

| id | task | size | status |
|---|---|---|---|
| A1 | **Mentat upsert/lookup resolution is O(store) per value**, which makes `import-csv` and every large `save_model` quadratic: 200k rows take 70 s, and 1M rows did not finish in 15 min. ## B. Scalability

Done since v0.10.0, all on `main`, for the record:
- one replication slot per database;
- the two-step `count_distinct`;
- the scoped `what_if`;
- linear `add_item`;
- name lookup hints;
- two-level reductions;
- fewer operators per measure;
- `CoordKey` as a small vector;
- two fewer FIXPOINT copies.

What remains:

| id | task | size |
|---|---|---|
| B1 | **Parallel apply in the logical worker.** One worker serves every model in a database on one core, so a slow model delays every other. Apply models in parallel: for example, a pool of dynamic background workers, one per busy model, under a configurable `improv.max_apply_workers`. The order within a model must stay the same, and the shared slot must still advance only after every model has applied the batch. **Acceptance:** with 4 models whose applies take 1 s each, a change to a fifth model is visible in < 200 ms; `logical.sh` and `scale.sh` pass; the shared-slot crash semantics are unchanged. | L |
| B2 | **[done]** (`feat(pg_improv): improv.commit_capture = 'rows', a scoped commit-mode recompute`. *Design note.* (b) loses: logical mode's fold state lives in the worker process, so a writer's backend cannot read it at its own COMMIT, and the worker is one poll behind the transaction anyway. (c) leaves 2.1 s per COMMIT. (a) reuses B3's scoped trigger-mode path, so it is cheap to build. It is opt-in, because the triggers are what commit mode exists to avoid. Triggers note each statement's touched coordinates per (model, table). A per-statement frame in the ExecutorFinish and ProcessUtility hooks checks that every write was captured; a write that was not (triggers disabled, replica role, a table bound later), a TRUNCATE, a partitioned or inherited table, a non-element-wise change, or more than 100k coordinates falls back to the full recompute. *Measured* at 2.5M rows, release, PG 18, per transaction, insert/COMMIT: a 1,000-row INSERT went from 4/2,090–2,115 ms (`relations`) to 5–6/142–159 ms (`rows`), under the 300 ms target. Ten one-row INSERT statements in one transaction: 2,090–2,110 → 111–112 ms. A 1M-row INSERT statement pays 2.24–2.27 s → 2.89–3.02 s (+30%) for its transition tables. `txn.sh` §3b and `privileges.sh` repeat their commit-mode checks with the capture) **Commit mode recomputes the written relations' dependents in full**: 2.1 s per transaction at 2.5M rows. The hook knows which tables were written, not which rows. Options (needs a design note): <br>(a) an opt-in transition-table trigger, `improv.commit_capture = 'rows'`, which costs ~1.5 ms per 1,000 rows and 35% on a 1M-row INSERT; <br>(b) reuse the logical worker's fold state when the database also runs logical mode; <br>(c) document commit mode as the small-model / correctness mode and leave it as is. **Acceptance:** a decision recorded, and either (a) or (b) built with a commit-mode 1,000-row batch at 2.5M rows < 300 ms, or the docs plus `status` saying so plainly. | M–L |
| B3 | **[done]** (`perf(pg_improv): trigger mode reads touched rows in one parallel scan per table`. The 290 ms was two serial full scans, one per binding: the scoped load ran through `Spi::get_one_with_args`, which pgrx executes read-write, so Postgres refused parallel workers, and each binding scanned the table again. Now one read-only, parallel scan per table finds the touched rows' `ctid`s, every binding reads them back by TID, `int`/`text`/`numeric`/`bool`/`uuid` dimensions compare natively so an index on them serves the scan, and only the in-scope result rows are read, through their primary key. Release, PG 18, 2.5M rows, no index: a one-row INSERT went 309–317 → 105–108 ms, 10 one-row INSERT statements in one transaction 2,864–2,968 → 901–906 ms, a 1,000-row INSERT 357–382 → 158–159 ms (≤ 350 ✓), a 1,000-row UPDATE 344 → 166 ms. With an index on the four dimension columns: 15 ms, 49–51 ms (3.3× one; main with the same index: 93–98 and 709–822 ms), 78–79 ms, and 100 ms. The < 2× target is not met. Ten statements touch ten sets of coordinates, so caching one statement's load cannot serve the next. Batching to COMMIT breaks read-your-writes (`tests/txn.sh` §2) unless every read first flushes the pending recompute through an executor hook. That design was weighed and not built: it is invasive, and it moves recompute errors from the INSERT to the read. The documented path is the index, at 3.3×) **Trigger mode costs ~290 ms per statement** on the 2.5M-row model (`load_scoped` 60%, `recompute` 19%, `read_results` 15%). Cache the scoped load per transaction, and batch statements within one transaction into one recompute at the last statement (or at COMMIT). **Acceptance:** 10 one-row INSERT statements in one transaction cost < 2× one; a 1,000-row statement stays ≤ 350 ms. | M |
| B4 | **Rebuilds are full reloads** (8–10 s at 2.5M rows). They happen on: restart, redefine, a new item in a category whose item list a formula reads, and a category crossing 1,024 items. <br>(a) Persist the fold state and engine snapshot so a restart resumes instead of rebuilding. <br>(b) Make the 1,024 crossing not invalidate `serves()`: block by item id from the first item. <br>(c) Let FILL and position-reading plans take the item list as data, so new items stop forcing rebuilds (the remaining P1-2 gap). **Acceptance:** restart → caught up in < 1 s plus WAL replay; a new Person under a FILL model applies without a rebuild. | L |
| B5 | **RANK, SORTBY and the per-item reductions re-run over the whole group**: 1–5 s per edit at 1M items. Build an order-statistics operator, a sorted arrangement that emits only the shifted range, as a custom DD operator. Needs a design note, and must respect the DD pin (`AGENT_ENGINE_STEERING.md` §2). **Acceptance:** an edit that moves one value k positions costs O(k log n); a new maximum is O(n) output, but no per-item recompute. | L |
| B6 | **Edit cost grows with the number of measures**: ~43 ms of progress tracking at 20k measures, even when the edit touches one. Split independent measure subgraphs into separate dataflows (or scopes), and route edits to the dataflow that reads them. **Acceptance:** an edit that reaches 1 of 20k measures costs < 5 ms. | L |
| B7 | **Memory: about 0.8 GB per million cells, and everything is in RAM.** <br>(a) Measure where the bytes are with a heap profile (dhat or heaptrack) at 1M/5M cells. <br>(b) Shrink the biggest holder: share arrangements between operators, and intern `CellValue` text. <br>(c) Out of core: build §3a of `AGENT_OUT_OF_CORE_DESIGN.md` (dimension partitioning) or decide it is post-1.0. **Acceptance:** a heap profile in the repo; ≥ 30% less memory per cell at 5M; a written out-of-core decision. | L |
| B8 | **FIXPOINT memory is ~1 kB per edge.** Share `W`'s arrangement between `Out`'s reduce and `M`'s join, and let the host step read `M` from it. Add delta-PageRank (feed only moving cells) once few cells move. **Acceptance:** ≤ 500 B per edge at 10M edges; the warm re-solve after one edge edit is ≥ 2× faster. | M |
| B9 | **Worker memory per model**: fold state plus engine is ~450 MB at 2.5M rows, and grows with distinct values (count_distinct) and with rows (min/max multisets). Measure it per model in `improv.status` (B-side of F3); consider spilling a min/max multiset to a btree in shared memory, or a per-model memory cap with a clear error. **Acceptance:** `status` shows each model's live memory; a cap (`improv.max_model_memory`) refuses or rebuilds with a logged reason instead of OOM-killing the backend. | M |
| B10 | **The DuckDB extension materializes every distinct coordinate in the engine**: 2.5M distinct cells take 16.5 s and 2.3 GB. Profile it (the engine path, not DuckDB), and stream results out instead of collecting them. **Acceptance:** 2.5M distinct cells ≤ 8 s, ≤ 1.5 GB. | M |
| B11 | **A scale regression gate in CI.** The benchmark was a one-off. Add a nightly or weekly workflow, at small sizes that fit CI, that fails when a probe regresses > 25% against a committed baseline. The full sizes stay a release-qualification step on EC2 (J3). **[done]** (`ci: a weekly scale regression gate`): `.github/workflows/scale-gate.yml`, `docs/reviews/bench/{scale-gate.py,reference.rs,baseline.json}`; each probe's time relative to a same-run reference workload, with a per-probe noise floor. | M |

## C. Security

| id | task | size |
|---|---|---|
| C1 | **The logical worker reads bound tables as the bootstrap superuser.** It calls `connect_worker_to_spi(db, None)`. It therefore bypasses row-level security and table privileges, and it publishes aggregates of rows the model's owner may not be allowed to see into result tables with ordinary grants. Run each model's load and apply as the model's owner (record the owner at `create_model`, and `SET ROLE` / `SetUserIdAndSecContext` per model), so RLS and GRANTs apply as they would for the owner. Document that a model's results are as visible as its result tables' grants, and that they aggregate what the owner can read. **Acceptance:** a test with an RLS policy on a bound table, where the owner sees half the rows, shows the model's results aggregate only that half, in every sync mode. **[done]** (5919cc9 `feat(pg_improv): record each model's owner`, 62db8af `fix(pg_improv): each model reads and writes as its owner`, and `fix(pg_improv): only those who may act as a model's owner change it`: row-level security on every `improv.*` table and a trigger on the owner, by the rule of `ALTER TABLE … OWNER TO`; `tests/privileges.sh`) | M |
| C2 | **Who may create a model over which table.** Today anyone with USAGE on `improv` and SELECT on a table can bind it. Decide and document the model: owner-based (C1) plus `REVOKE ALL ON SCHEMA improv FROM PUBLIC` by default, with a `improv_admin` role. Add an `improv.models` view filtered to what the current role owns or has been granted. **Acceptance:** a privilege matrix in the docs, tested by `tests/txn.sh` or a new `tests/privileges.sh`. **[done]**: done, the owner-based half (C1): a model reads and writes as `improv.model.owner`, documented in the pg_improv README's "Privileges", and `tests/privileges.sh` checks RLS in every sync mode and a revoked SELECT; only a role that may act as a model's owner changes it or its owner (C1), and the README's Privileges has a first matrix of who may read and change what. Done too, item keys: `improv.item` (the bound tables' keys) is readable only by those who may act as the owner, as `cell` and `meta` are, and `what_if` is theirs, computing as the owner; the README documents giving it to others (a SET member, or a per-model `SECURITY DEFINER` wrapper), tested in `tests/privileges.sh` **[done]** (with the commit). Done too: the `improv_user` role (what a non-superuser needs to build models; result schemas are the extension's, so no `CREATE` on the database) and `improv_admin` (enrolls builders, acts on no one else's model: acting on a model is acting as its owner), both made `IF NOT EXISTS` and kept by `DROP EXTENSION` (32d88b8); `improv.models` (cfab2c3); the full privilege matrix in the README's Privileges, checked cell by cell by `tests/privileges.sh` (with this commit). **[done]** | M |
| C3 | **External security review** of pg_improv and the HTTP server: SQL injection in generated SQL, `SECURITY INVOKER` paths, search_path, the extension upgrade scripts, pgspot findings, the server's auth and CORS. Fix all highs before 1.0. **Acceptance:** a review report in `docs/reviews/`, with every high and medium closed or accepted with a reason. | M |
| C4 | **The HTTP server.** Bearer-token auth exists (`IMPROV_API_TOKEN`). Still needed for 1.0: TLS guidance (behind a proxy, or rustls directly), per-token read/write scopes, request size and rate limits, and an audit log of writes. Required before I1 (web GUI). **Acceptance:** `docs/src/server.md` deployment section; the tests cover the scopes and limits. **[done]** (`feat(server): token scopes, limits, a write audit log, /v1 and OpenAPI`: TLS through a reverse proxy, documented with Caddy and nginx examples) | M |
| C5 | **Supply chain.** Release artifacts get SHA-256 sums and signatures (cosign or minisign), plus an SBOM (`cargo cyclonedx`) attached to each GitHub release. `cargo deny` stays in CI (it caught RUSTSEC-2026-0381/0382). **Acceptance:** `release.yml` attaches sums, signatures and SBOM; CONTRIBUTING documents verification. **[done]** (`ci(release): SHA256SUMS, cosign keyless signature and SBOMs`: `ci/release-attest.sh`, tested locally except the keyless signing, which only runs in Actions) | S |

## D. Postgres operations and correctness

| id | task | size |
|---|---|---|
| D1 | **Physical standbys and failover.** The worker does not run on a hot standby, and a failover has never been tested. Test streaming replication: results replicate as ordinary tables; after a promotion, the worker on the new primary recreates the `improv_db` slot (logical slots do not survive failover unless PG 17+ failover slots are used) and rebuilds each model. Support `failover = true` slots on PG 17+ (`pg_create_logical_replication_slot(..., failover => true)`) where available. **Acceptance:** `tests/failover.sh` (primary, standby, promote) passes on PG 17 and 18, with the model in sync after promotion. **[done]** (`feat(pg_improv): failover slots, and a failover test`) | M |
| D2 | **`pg_upgrade`** of a cluster with logical-mode models (PG 17 → 18). `pg_upgrade` carries logical slots only when the old cluster is PG 17 or later. Test it, then document the procedure (drop the slot, upgrade, let the worker rebuild). **Acceptance:** `tests/pg_upgrade.sh`, plus a runbook section (F5). **[done]** (`feat(pg_improv): pg_upgrade carries logical-mode models`; procedure in `crates/pg_improv/README.md` "pg_upgrade") | S–M |
| D3 | **Partitioned tables in logical mode.** Commit mode maps partitions; logical mode is barely tested with them. The publication needs `publish_via_partition_root = true`, or per-partition routing. **Acceptance:** `logical.sh` covers range-partitioned and list-partitioned bound tables, including attaching and detaching a partition. **[done]** (`fix(pg_improv): logical mode follows partitioned tables`) | S–M |
| D4 | **[done]** (`fix(pg_model): fold text min/max under the column's collation, sum floats exactly`: (a) a text `min`/`max` folds under the value column's collation, bytes for C/POSIX and `varstr_cmp` for other deterministic ones; at 2.5M rows a change is visible in ~90 ms, was ~3,000 ms (a rebuild each); (b) a nondeterministic collation's `min`/`max`/`count_distinct` rebuilds, reason `nondeterministic collation`; (c) float sums keep an exact fixed-point accumulator, order-free; the one-rounding-vs-scan-order gap is a documented, tested limit in postgres.md) **Collations and types in the live folds**, all marked `shortcut:` in `pg_model/src/live.rs`: <br>(a) text min/max rebuilds on every change: fold it under `COLLATE "C"` when the binding's collation is deterministic, or keep a collation-sorted multiset; <br>(b) `count_distinct` compares text forms, so a nondeterministic collation is not handled: refuse it at bind time with a clear error, or support it; <br>(c) float sums with >9 decimals or exponents differ from a fresh sum in the last bits: document, or keep an exact decimal accumulator. **Acceptance:** each `shortcut:` resolved or turned into a documented, tested limit. | M |
| D5 | **[done]** (`fix(engine): SUM and AVERAGE are Neumaier-compensated in every path`: decided for Neumaier; the 1M-item SUM edit is 0.30–0.33 ms p50 either way, evaluate 1.5–1.6 s; 1M values cost 1.3 ms vs 0.5 ms naive; over 40 seeds × 3 shapes of 10k values, naive flat misses mpmath's exact sum by up to 1,363 ulps and the two-level by up to 92, Neumaier by 0, flat and blocked equal; goldens in `tests/sum_10k.rs` from `scripts/goldens/sum_10k.py`; no existing golden changed) **Large sums above 1,024 items are a fixed two-level summation**, so the last bits differ from v0.10.0. Decide whether 1.0 promises Kahan/Neumaier for SUM and AVERAGE everywhere (deterministic, closer to exact), and pin it with goldens. **Acceptance:** a decision in `formulas.md`, and goldens for a 10k-item fractional SUM. | S |
| D6 | **Upgrade path from every released version to 1.0**: 0.8.0, 0.8.1, 0.9.0, 0.10.0 and 0.11.0 → 1.0.0, in `tests/upgrade.sh`. **Acceptance:** the matrix runs in CI on PG 15–18. **[done]** (`test(pg_improv): upgrade from every release on every major`): every release's update-script chain and `ALTER EXTENSION UPDATE` path checked; each release that builds for the major (0.8.x: PG 17 only; 0.9.0 and 0.10.0: 15–18) updated with a model in each of its sync modes, checking results, owner and RLS, the worker, `define`, `pg_dump`, commit mode. | D7 | **Fail safe on resource limits.** `max_replication_slots`, `max_wal_senders` and `max_worker_processes` exhausted; `wal_keep_size` exceeded; disk full while writing results. Each needs a clear `last_error`, no crash loop, and no unbounded WAL retention: the slot must not pin WAL forever if the worker is down. Add `improv.max_slot_lag` (default e.g. 4 GB): past it, drop and rebuild instead of retaining WAL. **Acceptance:** a test per limit; `status` shows the condition. **[done]**: done (`feat(pg_improv): improv.max_slot_lag, and survive exhausted slots`, `logical.sh` 14–14c): `max_slot_wal_keep_size` exceeded (D11), `improv.max_slot_lag`, `max_replication_slots` exhausted. Done too (with this commit, `tests/limits.sh`): `max_worker_processes` exhausted (the postmaster logs it once and does not retry; `status` reports the worker not running and names the setting), `wal_keep_size` (not a limit: a slot keeps its WAL at `wal_keep_size = 0`; `lag_bytes` shows it), disk full while writing results (`last_error`; the failed apply now aborts, so nothing is half-written; the worker and the other models keep going and the model recovers; trigger mode fails the writer). | D8 | **The idle worker floods the server log.** On PG 18 every poll's peek logs "starting logical decoding for slot improv_db" and "logical decoding found consistent point" at LOG, about 310 MB a day at `poll_ms = 200`. | D9 | **A config reload never reaches the worker.** pgrx 0.17's `wait_latch` does not call `ProcessConfigFile`, so `improv.poll_ms` and `improv.max_changes` change only after a worker restart. Call it on SIGHUP. **Acceptance:** `logical.sh` sets `improv.poll_ms` with `ALTER SYSTEM` and `pg_reload_conf()`, and the new interval takes effect without a restart. **[done]** (`fix(pg_improv): the sync worker rereads its configuration on SIGHUP`) | S |
| D10 | **[done]** **A plain restore of a commit-mode model.** `pg_restore` without `--single-transaction`, or `psql -f` of a plain dump, loads each table's data in its own transaction and adds primary keys after all of it. A bound table's COPY then committed, the commit hook recomputed, and its upsert into a result table with no key yet failed ("no unique or exclusion constraint matching the ON CONFLICT specification"), aborting the restore. **Fix:** a commit-mode recompute is skipped, with a NOTICE, while one of the model's result tables has dimension columns but no primary key (only a restore makes that); the dump carries the results, and the next write or `recalc` recomputes. | D11 | **An invalidated slot stops sync silently.** Once `max_slot_wal_keep_size` invalidated `improv_db` (`wal_status = 'lost'`), every poll logged "can no longer access replication slot", `status` showed no error, and results stopped following writes. Drop and recreate the slot, reset every model's progress so each rebuilds, log it once, and show it (and any other slot failure) in `last_error`. **Acceptance:** `logical.sh` loses the slot while the worker is away, and the models then rebuild, equal a fresh `recalc`, and `status` reported the condition. **[done]** (`fix(pg_improv): recover from an invalidated slot`) | S |
| D12 | **Logical mode outside `improv.database` is accepted and never served.** `set_sync_mode(m, 'logical')` succeeds in another database, and `status` reports no error, with `lag_bytes` read from the other database's slot of the same name. Refuse it (in `set_sync_mode` and `bind_measure`), with a HINT naming the setting; `status` joins the slot on the database and reports the missing worker. **Acceptance:** `logical.sh` with a second database. **[done]** (`fix(pg_improv): refuse logical mode where no sync worker runs`) | S |
| D13 | **`DROP EXTENSION pg_improv CASCADE` leaves the slot retaining WAL forever.** The worker sees no extension and does nothing. When the extension is gone and an `improv_db` slot exists in the database, drop it and the publication, and log it once. Document the clean order (`drop_model`, then `DROP EXTENSION`) and what a bare drop leaves behind (the result schemas, kept as user data, and the replica identity). **Acceptance:** `logical.sh` drops the extension with a logical model, then the slot and publication are gone within a few polls. **[done]** (`fix(pg_improv): drop the slot DROP EXTENSION leaves behind`) | S |

## 1.0.0 exit criteria

Improv is 1.0.0 when all of these hold:

1. **No open blocker:** A1 landed; every task in B–J is done or explicitly
   moved to "Not planned for 1.0" below, with a reason.
2. **Security:** C1–C3 done. The worker respects RLS and privileges, there is
   a privilege model, and the external review is closed.
3. **Operations:**
   - failover (D1), pg_upgrade (D2) and backup/restore (F5) are tested by
     scripts in CI or in J3;
   - resource limits fail safe (D7);
   - the 72-hour soak passes (J4).
4. **Documentation:**
   - F1–F7 are published; F8's tutorials run in CI;
   - every CLI tool has a man page (G2) generated from its parser (G1);
   - F10's review is done.
5. **Front ends:** H1's findings closed or deferred with reasons; H2's
   accessibility blockers fixed; I1 decided (and I2 built if the decision is
   to ship a web GUI in 1.0; it is not: see I1).
6. **Stability promise:** J1 published, and the formula language, SQL API,
   file schema, CLI and HTTP API reviewed against it.
7. **Quality gate:** the existing gate (fmt, clippy, tests, coverage ≥ 90%,
   docs, Verus, GUI golden, pg_improv on PG 15–18, DuckDB 1.5.6 + 2.0) green,
   and the scale regression gate (B11) green.
8. **Qualification:** J3 run on the release candidate, numbers in the
   release notes.

## Not planned for 1.0

Each entry below is moved here only with a reason.

- **A billion-row engine.** Out-of-core is decided in B7, but building it is
  not a 1.0 requirement. The 1.0 promise is "models whose cells fit in
  memory", with the limits stated in F2 and F4.
- **A web GUI (I2) and multi-user editing (I3).** I1 decided (c) for 1.0:
  the `/v1` HTTP API, documented, is what a web front end builds on. The
  spike (`crates/gui_web`, branch `work/web-spike`) shows the egui GUI runs
  in a browser over `improv-server`; what I2 needs first is server work (a
  GUI-shaped API, a change feed, static hosting) and an answer for screen
  readers, since egui's web runner drops AccessKit. See
  `docs/reviews/2026-10-22-web-gui.md`.
- **Replacing a graph database.** FIXPOINT covers iterative models like
  PageRank up to the tested size; F2 says where to stop.
