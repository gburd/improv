# Improv v0.11.0 release qualification (J3)

The road-to-1.0 plan's J3 run on the 0.11.0 release candidate:
the [v0.10.0 benchmark](2026-10-20-v0.10.0-benchmark.md)'s cases, at its sizes,
against the previous release. Rule: within 10% of 0.10.0, or explained.

## Regressions and explanations

**PG 17's first `scale.sh`: batches 220–1,742 ms.** Every other run (PG 17 twice more, PG
18 twice) kept all six batches in 83–145 ms. One run in five, not repeated in two reruns
of the same build on the same PG; the batches are commit → visible, so a checkpoint or
autovacuum on the 2.5M-row table during the batches would show this way. Not chased
further; the scale gate's `pg_scale` probe watches the trend.

**FIXPOINT memory, B8.** 0.11.0 holds 556 B per edge at 10M edges (0.10.0: 845); the plan's
target, 500 B, is not met. The CHANGELOG says so; the rest stays B8.

**Peak RSS of the folded DuckDB query is higher** (430/490 MB → 490–630 MB). DuckDB's own
working memory: 0.10.0 ran with 32 threads, this box has 48. At `SET threads = 32` it is
407–503 MB on v1.5.6 and 460–472 MB on v2.0, the same as 0.10.0.

**Idle worker CPU at 1,000 models: fixed after the candidate.** The 1,000-model worker idled
at 0.14 of a core, then 0.27 once autovacuum analyzed `improv.model`: 43% of its time was in
LLVM, JIT-compiling the per-poll queries, whose estimates then passed `jit_above_cost`. `fix(pg_improv): the
sync worker's session runs with jit = off` holds it at 0.11 across the autoanalyze, and
`scale.sh` at 2.5M still passes (batches 84–114 ms). 0.10.0's 0.02 core idle at 1,000
models is not comparable: its slot per model decoded so slowly that a sweep took longer than the 10 s sample.

### The scale gate failure

The weekly gate's first run on the candidate reported `wide.rank.edit_tail` at 1.25× the
baseline, its limit; the rerun read 0.98×. An interleaved A/B on the box (5 runs each,
`RANK(X OVER W)` over 100k items, the gate's size) of `9e74dda` (the last green gate) and
`c189404`, medians:

| | `9e74dda` | `c189404` | | runs slower |
|---|---:|---:|---:|---:|
| evaluate | 162.8 ms | 164.7 ms | +1.2% | 5 of 5 |
| `Engine::new` | 168.2 ms | 164.0 ms | −2.5% | 0 of 5 |
| edit, new max | 136.1 ms | 144.5 ms | +6.1% | 5 of 5 |
| edit, tail | 39.1 ms | 40.9 ms | +4.4% | 4 of 5 |

So the candidate's RANK edits are slower by about 5%, consistently: within the 10% rule
and far below the 25% gate, which the first run reached only with runner noise on top
(this probe read 1.10–1.25× on earlier gate runs that changed nothing near it). The cause
is not found: RANK does not go through the exact sum, so the candidates are the changes to
the live engine since `9e74dda` (`perf(engine): 63% less memory per cell`, `fix(engine): a
category growing past 1,024 items keeps the live engine`, and the 8 MiB engine thread).
Not profiled; recorded so the next gate run can tell drift from noise. At 1M items the same
edits are 37–57% faster than 0.10.0 (the table above).
