## 1. pg_improv full-size acceptance (`tests/scale.sh`, ROWS=2500000 BATCHES=1000)

2,500,000 fact rows into 44,750 coordinates (Person × Year × Release × Scope), with `count` and
`count_distinct` bindings. Both runs PASS. PG 17 was run twice; the table shows the second run,
which was the first with the RSS breakdown (the first run's numbers: REFRESH 4,898 ms, recalc
5,925 ms, initial build 9,022 ms, batches 82/98/144/144 ms).

| | PG 17.11 | PG 18.6 |
|---|---:|---:|
| Load 2.5M rows (INSERT … SELECT) | 6,766 ms | 6,767 ms |
| `REFRESH MATERIALIZED VIEW CONCURRENTLY` (same GROUP BY) | 4,870 ms | 4,784 ms |
| `improv.recalc` (load, compute, write 44,750 × 2 cells) | 5,943 ms | 5,851 ms |
| Worker's initial build (slot, load, fold seed, engine) | 9,100 ms | 8,776 ms |
| 1,000-row batch, commit → visible (6 batches): min / median / p95 / max | 82 / 112 / 113 / 113 ms | 114 / 114 / 142 / 142 ms |
| Batch bringing a new Person item | 112 ms | 114 ms |
| `rebuilds` / `incremental_applies`, scale model, after the batches | 1 / 6 (initial build only; no rebuild) | 1 / 6 |
| 1,000 random INSERT/UPDATE/DELETE batches (commit time) | 9,368 ms | 8,571 ms |
| Random-batch model: `incremental_applies`, `rebuilds` | 0 → 95, 1 → 1 | 0 → 95, 1 → 1 |
| Random-batch correctness | count and sum equal a fresh `recalc`; count_distinct equals `count(DISTINCT sha)`; shared-key delete keeps the distinct count: **PASS** | **PASS** |

The script times only 6 batches (5 existing-person + 1 new-person) at 2.5M rows. `BATCHES=1000`
sets the number of random batches in part 2, which runs on its own 2,000-row table. 1,000 random
batches produced 95 incremental applies because the worker coalesces whatever has committed when
it polls (`improv.poll_ms = 50`). The batch latency floor is set by that poll interval plus the
script's 20 ms visibility poll, so 82 to 142 ms means about one or two poll cycles.

The L1 to the plain-Rust reference is 2.1e-15 to 4.4e-15 at every size, before and after the edit.

**Where time and memory go.** Close to linear in the edge count, with no cliff up to 20M edges.
Per-edge costs creep up about 50 % from 1M to 20M edges: a cold round goes from 0.15 to 0.22 µs
per edge, a warm round from 0.09 to 0.14 µs, and build plus solve from 6.6 to 10.2 µs. About
70 % of build plus solve is outside the solve (in the dataflow build of `Out`, `M` and
`Dangling`, and the seed). With the model and the live engine alone, memory is **about 1.7 kB per
edge** (15.9 GB at 10M, 31.8 GB at 20M; those runs skipped the fresh evaluate). Up to 5M the peak
is about 3 kB per edge (3.1 GB at 1M, 14.5 GB at 5M), because the test's from-scratch `evaluate`
cross-check runs while the engine is still alive: the 50k timeline shows 7.8 GB after the warm
re-solve, rising to 14 GB in the fresh evaluate. That puts the box limit, 50 GB, at roughly
**30M edges** (about 300k nodes at this density); 20M edges / 200k nodes
was the largest size run. `distance()` (it sorts every cell's key per round) costs 2 % of a
solve, and the host `refresh` is negligible.

Profile at 10k / 1M (`perf record --call-graph dwarf`, inclusive). 79 % of the time is on the
engine worker thread: timely/differential operator scheduling takes 41 % (the build of
`M = W / Out` and the joins, with `MergeBatcher::merge_by` on `((CoordKey, (CoordKey, CellValue)))`
the hottest DD frame). `solve_fixpoints` takes 28 % (`Host::step` → `Host::aggregate` 23 %,
`Shape::fill` 11.7 % self, `hosteval::emit` 3.5 %). malloc and free take 16 % and 12 %
inclusive. The rest is the test thread: `graph()` / `Model::set_input` at 7.9 %, and the hashing
of `(MeasureId, Coordinate)` keys. Flat profile at 20k / 2M (`-F 499`, self time): `Shape::fill`
8.8 %, DD `merge_by` 5.0 % + 3.3 % + 1.5 %, malloc 3.8 %, free 3.6 %, `hash_one(Vec<(u32,u32)>)`
3.2 %, the test's reference loop 3.2 %, `hash_one((MeasureId, Coordinate))` 2.5 %,
`reduce::statistical::sum` 2.2 %, `hosteval::value` 2.1 %, `union_keys` 1.7 %.

So a FIXPOINT round re-reads every edge (`Shape::fill` refills the laid-out rows each round, as
the code's `shortcut:` comment says). The memory per edge suggests every edge is held several
times: as `Model.inputs`, in DD arrangements (`W`, `M`, the join), and in the host evaluator's
layout. That is an inference; heap attribution was not measured.

Building the 1M-item category itself is fine through the struct fields (0.16 s). Through the
public `Model::add_item` it is **O(n²)**: 10k items 15 ms, 30k 128 ms, 100k 1.37 s, 300k 12.3 s
(it does `c.items.contains(&id)` on a `Vec` for every insert). 1M items through `add_item`
would take about 2 minutes. `pg_model::build_model` (every pg_improv load) calls it once per
item, and `ItemInterner::register` (CSV/SQL import) has the same `contains` loop. The probes
used the fast path so they measure the engine, not this.

The engine's whole-group reductions are not incremental inside a group. One cell edit re-runs
the group's reduce over all n inputs: `SUM` 0.6 µs, `RANK` 1.3–3.6 µs and `SORTBY` 1.8–4.4 µs per
item per edit. At 1M items an edit costs 0.6 s for SUM and up to 5.4 s for SORTBY/RANK. `PREV`
stays O(1) per edit.

Profiles. **RANK at 1M** (whole run, `-F 299 -g`): `reduce::statistical::per_item_ok` closure
6.3 %, timely `StreamCore` 4.0 %, DD `MergeBatcher::merge_by` 2.9 %, `dataflow::agg_rows` 2.7 %,
DD `BatchContainer::advance` 2.6 %, and malloc/free/memcpy at about 20 % combined. Every edit
rebuilds the group's `Rows` (`agg_rows`) and re-ranks it. **Fan of 20k measures**: timely
progress tracking leads: `BinaryHeap::pop` (pointstamps) 4.2 %,
`Subgraph::propagate_pointstamps` 4.1 %, `Subgraph::schedule` 3.2 %, `ChangeBatch::compact`
2.1 %. One edit round schedules every operator of every tracked measure.

| | 200 models | 1,000 models |
|---|---:|---:|

Memory is about 0.6–0.7 MB per small model, which is fine. **Latency is the problem: the single
worker polls every model in turn, and each model's poll costs about 25 ms (at 200 models) to
120 ms (at 1,000) of logical decoding, even when that model's tables did not change**, so one change waits for up to one full sweep (about
N × poll cost). Worker profile at 1,000 models (`perf --call-graph dwarf`, 15 s):
`pg_logical_slot_peek_binary_changes` 83 %, `LogicalDecodingProcessRecord` 81 %, `xact_decode` 69 %,
`LocalExecuteInvalidationMessage` 39 %, `hash_seq_search` **36 % self**, `RelationIdGetRelation` 12 %.
Every slot re-decodes the same shared WAL, and each poll starts its own decoding context. The
catalog-invalidation messages in that WAL appear to be replayed per slot per poll, each a
`hash_seq_search` over a relcache that holds thousands of relations; that is the likely source
of the 36 %, but it is inferred from the profile and was not traced. All 1,000 slots were 40 MB
behind the WAL head during the apply-latency phase. `standby_decode` /
`SnapBuildProcessRunningXacts` (4 %) are the running-xacts records: one is logged by
`pg_log_standby_snapshot` after each advancing poll, and every other slot then decodes it.

### 3g. Storage: improv CLI `import-csv` into Mentat (SQLite)

CSV `t,p,r` (Time × Product, distinct coordinates), `import-csv m.db f.csv 100 Qty r t:1:Time p:2:Product`.

| Rows | `import-csv` | Peak RSS | DB size | `eval` (load_partial + evaluate) | `list` (load_model) | `export` (JSON) | `set` one cell (load + save) |
|---:|---:|---:|---:|---:|---:|---:|---:|
| 50,000 | 4.7 s | 47 MB | — | | | | |
| 100,000 | 18.7 s | 72 MB | 120 MB | 0.74 s | 0.55 s | 0.50 s | 1.02 s |
| 200,000 | 70.5 s | 124 MB | 239 MB | | | | |
| 300,000 | 171 s | 182 MB | 359 MB | 2.57 s | 1.87 s | 1.69 s | 3.91 s |
| 1,000,000 | **killed at the 15-min cap** (est. about 30 min) | 575 MB at kill | — | — | — | — | — |

**Import is quadratic**: 4.7 → 18.7 → 70.5 → 171 s for 50k → 100k → 200k → 300k rows, so about
×4 per doubling. Load and save of an existing store are linear (about 6–13 µs per cell) and fine.
Profile of the 1M import (`perf --call-graph dwarf`, 20 s): `ModelStore::save_model` →
`transact_group` → `mentat_db::tx::transact` → `MentatStoring::resolve_avs` **89.7 %** →
`sqlite3_step` → `sqlite3BtreeTableMoveto` 65 %, `readDbPage`/`pread` 40 %, `walFindFrame` 10.5 %.
The query is mentat_db 1.16.0's
`WITH t(search_id, a, v, value_type_tag) AS (VALUES …) SELECT t.search_id, d.e FROM t, all_datoms AS d WHERE d.index_avet IS NOT 0 AND d.a = t.a AND d.value_type_tag = t.value_type_tag AND d.v = t.v`.
Its `EXPLAIN QUERY PLAN` shows the `UNION ALL` arm of the `all_datoms` view (the
`fulltext_datoms` side) running `SEARCH datoms USING INDEX idx_datoms_avet (a=? AND
value_type_tag=?)`, which drops `v`. That arm scans every datom of the attribute per lookup
value. Measured on the 100k store: **one lookup through `all_datoms` takes 84 ms, against 0.07 ms
through `datoms`** (100,000 avet rows on attribute 65550, `fulltext_datoms` empty). Every cell's
upsert resolves its `[a v]` this way, so the import is O(cells²).

### 3h. DuckDB: `improv(source, model)` (extension built from the tag with `make configure release`)

`contribution_rows` in DuckDB: 2.5M rows, 44,750 coordinates. Model: 4 categories,
`input N = id count`, `input Amount = amount sum`, `Contributions = N * 1`,

Results are correct: sum(Contributions) = row count, sum(Share) = 180 buckets. The fold runs in

loads into both CLIs.

## Ranked scalability issues (worst first)

1. **Mentat import is O(cells²): 1M-row `import-csv` does not finish in 15 min.** 100k rows take
   18.7 s, 300k take 171 s, 1M was killed at 900 s. 90 % of the time is in mentat_db's
   `resolve_avs`, whose `all_datoms` UNION ALL arm cannot use `v`: 84 ms per lookup against
   0.07 ms on `datoms`, at 100k datoms. *Fix:* in mentat_db, query `datoms` directly when no
   attribute in the batch is fulltext (or add `v` to the fulltext arm's predicate so it can
   seek), release, and bump the pin.
2. **pg_improv's single sync worker does not scale with the number of logical models.** At 1,000
   small models, one-row apply latency is 12–120+ s and a write touching all models takes 201 s.
   200 models already show 0.3–4.9 s. 83 % of the worker is
   `pg_logical_slot_peek_binary_changes`, re-decoding shared WAL once per slot per poll, with
   `hash_seq_search` at 36 % (likely invalidation replay). *Fix:* use one slot and publication per
   database, routing changes to models by relation (or skip the peek for models whose tables'
   `pg_stat` counters did not move), and stop calling `pg_log_standby_snapshot` after every
   model's advance.
3. **Every recompute path in pg_improv re-reads the whole fact table, and `count_distinct` loads
   through a 2.5M-row sort.** `commit` mode costs 5.6 s per transaction at 2.5M rows,
   `what_if` 5.4 s, `recalc` 5.9 s, storage_pg open 5.7 s, and trigger mode 290 ms per
   statement. In every case 75–78 % of the time is `load_scoped`, and 5.0 s of it is the
   `count(DISTINCT commit_sha)` GroupAggregate sort. *Fix:* load `count_distinct` through
   `SELECT DISTINCT dims, v` then `count(*)` (950 ms, measured), with `COLLATE "C"` on the keys.
   Then let commit mode and `what_if` reuse the trigger path's coordinate-restricted recompute,
   or the worker's live fold state, instead of a full load.
4. **`Model::add_item` and `ItemInterner::register` are O(n²) in a category's item count.**
   300k items take 12.3 s through `add_item`. A DuckDB `improv()` over one 300k-item category
   takes 38 s, 89 % of it in `build_model` and `register`. It hits every pg_improv load,
   DuckDB query and CSV/SQL import with a wide category. *Fix:* keep a `HashSet<ItemId>` per
   category, or check `model.items` membership, which is already a HashMap, instead of
   `Vec::contains`.
5. **Whole-group reductions are not incremental inside a group.** One cell edit under
   `SUM`/`RANK`/`SORTBY` over a 1M-item category costs 0.6 s / 1.3–4.6 s / 1.8–5.4 s, because DD
   `reduce` re-runs over the whole group (`agg_rows` plus `per_item`). *Fix:* make
   `SUM`/`COUNT`/`AVERAGE` invertible aggregates (apply the delta), and for RANK/SORT emit only
   the shifted range (or use a sorted arrangement with an order-statistics index).
6. **Edit latency grows with the number of tracked measures, not with what the edit touches.**
   It costs 15–37 µs per measure per edit (742 ms at 20k fan measures), mostly timely progress
   tracking (`propagate_pointstamps`, the `BinaryHeap` pops). *Fix:* split independent measure
   subgraphs into separate dataflows (or scopes), or batch edits so one round's progress cost
   amortizes.
7. **FIXPOINT memory is about 1.7 kB per edge**, so the box tops out at about 30M edges (20M took
   31.8 GB). Time is near-linear: 6.6–10.2 µs per edge to build and solve, a 4.4 s round at 20M
   edges.
   Every round refills every edge (`Shape::fill`, the known `shortcut:`). *Fix:* store `W`/`M`
   once (the host evaluator could borrow the arrangement instead of its own layout), and the
   known delta-PageRank step once few cells move.
8. **Engine `evaluate` is mildly superlinear and memory-heavy**: 0.7–0.9 GB and 4.7–5.5 s per
   M cells, so a 5M-cell grid takes 27 s and 3.6 GB. It holds no cliff, but 50M cells would
   need about 36 GB. *Fix:* intern `CoordKey`s (today a `Vec<(u32,u32)>` heap allocation per
   cell; malloc/free and `hash_one(Vec<(u32,u32)>)` lead every profile) as fixed-width
   packed keys.
9. **Name lookups are linear scans** (`Model::measure_by_name`, `category_by_name`), which makes
   bulk define quadratic: parsing 20k measures takes 0.5 s (110× the 2k time), and 20k lookups
   over 20k measures take 1.5 s. It is minor at today's model sizes. *Fix:* keep a name → id index on `Model`.

## What held up

- pg_improv logical mode at the acceptance size, on both majors: 2.5M rows, batches visible in
  82–142 ms, no rebuilds, correctness PASS, about 450 MB private worker memory, flat across batches.
- Sparse 6-category models (10^6 cells): about 3 s per reduction in any direction.
- `PREV` along 1M items: O(1) edits (0.06–0.34 ms).
- Single-cell edits on grids: 64 µs regardless of size (10k to 100k).
- DuckDB `improv()` over 2.5M fact rows: 0.65 s, flat in the row count, on v1.5.6 and v2.0.
- Mentat load and save of an existing store: linear.
